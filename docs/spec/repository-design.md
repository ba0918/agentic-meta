# agentic-meta リポジトリ設計

このリポジトリの設計上の決定事項を記す。ロードマップの実行手順(wave 分割や移植順序)は
実装計画側の管轄であり、ここには「何を作るか・何を不変条件とするか」だけを置く。

## 目的と位置づけ

agentic-meta は、肥大化した claude-skills リポジトリを責務で3分割したうちの1つで、
「エージェント能力そのものを作る・評価する」スキル(メタスキル)を収める。

3リポジトリは対等な製品ではなく、意図的に非対称とする。

| リポジトリ | 性格 | 独立性 |
|---|---|---|
| agentic-rules | 作業中に守る規範 | 単独製品(達成済み) |
| agentic-workflow | 仕事の進め方 | rules を前提とする統合製品。内部スキル間の結合は許容 |
| agentic-meta(本リポジトリ) | 能力の測定・評価・改善 | 単独製品 |

workflow に単独性を求めないのは、計画作成や壁打ちなどの単機能ではフローとして
成立しないため。逆にメタスキルは任意のスキル集合に対する汎用の測定・改善ツール
として単独で有用であるため、単独製品として成立させる。

## 単独成立の合格条件

「未知の第三者製スキル集でも動く」を、測定可能な形で次のように定義する。

> 構造・語彙・ログ形式の異なる複数の検証用 fixture に対し、汎用フォールバック
> または対象側アダプターのみで完走すること。

一例で動くことは偶然の互換性を排除できないため、合格条件としない。この fixture 群
自体を本リポジトリの成果物として整備する。

## agentic-workflow との関係 — 依存ではなく退化

メタスキルの本体は workflow のスキルを知らない。過去に存在した実行委譲
(例: 改善案の適用を iterate / cycle に投げる)は本体から切り離す。

workflow が存在する環境では統合が「格上げ」として働き、存在しない環境では
スキルが必要なものを明示して report-only 等に退化する(graceful degradation)。
依存を宣言して解決するのではなく、失敗を明示して人間またはエージェントに
解決を委ねる方式を採る。黙って壊れることを禁止する。

## 共有文書の扱い — 3軸 triage

旧 claude-skills の skills/shared/(契約文書約30本)は「共有文書」という単一分類を
やめ、各文書を3軸 — 再導出可能性・変更結合度・実行時必須性 — で判定して
行き先を分ける。

| 種別 | 行き先 |
|---|---|
| 知識文書(設計原則・テスト規範など) | agentic-rules のスキル名参照に置換。vendor しない |
| 短く再導出可能な記述 | 各スキルへ複製、または SKILL.md に直接記述 |
| 出力契約(成果物フォーマットを規定するもの) | 契約ID + 内容 digest を備えたプロトコルとして vendor(適合テストは持てる契約が持つ) |
| workflow の運用契約 | agentic-workflow 内部に残留。本リポジトリは関知しない |

出力契約を「文書」でなく「プロトコル」と呼ぶのは、コピーの一致検証(drift 検出)
だけでは契約とスキルの意味的互換を保証できないため。digest による同一性の証明に
加えて、適合テストを契約自体に持たせられるなら持たせる。

ただし適合テストを置けない契約がある。条項が静的な形ではなく実行時のふるまい
(対象の探索順・書き込み先・作業コピーの扱いなど)を縛る場合、テストは条項を
コードで言い直した第 2 の実装になり、本文を直したときに黙ってずれる。ずれない
形で書けないと判断したときは、適合テストを持たないことを選んでよい。その場合は
なぜ持たないかを契約本文に記す(`contracts/fixture-contract.md` が最初の例)。

互換性の判定そのものは vendoring の責務外で、消費側の regression 機構の管轄とする。

## vendor 機構(宣言駆動・ツール外部化)

vendoring(正本の共有文書を各スキル配下へ展開し、コピーの本文が正本の本文と
バイト同一であることを保証する機構)は、外部ツール `@ba0918-dev/agentic-skill-vendor`(npm)に
委ねる。ツールは devDependency として導入し、lockfile で版を固定する。
digest 規則(本文の正規化を含む)・vendored copy のヘッダ形式・violation kind
といった機構仕様の正本はツール側リポジトリにあり、本リポジトリには複製しない。

- 契約の正本はリポジトリ内 `contracts/<id>.md` に1部だけ置く(id はファイル名)
- 各スキルは SKILL.md frontmatter に契約 id のみを宣言する。digest は書かない
  (宣言は「安定した依存の意図」、pin は「現在の採用内容」で責務が別)
- digest pin は中央 lock(`vendor-lock.json`)に置く。lock は dependencies
  (スキル → 契約 id 列)と resolutions(契約 id → digest)を分離した正規形で、
  ツールの `gen` が正本に合わせて書き直す導出スナップショットである
  (package.json と lockfile の関係と同じ)。専用の承認コマンドは持たず、門番は
  PR レビュー。`gen` の `adopted: <id> <旧digest> -> <新digest>` 報告と lock の
  git 差分が、消費側 regression 機構が証跡を突き合わせる結合点になる
- CI と pre-push は `verify`(ツリー対 lock)と `lint-selfcontain`(自己完結性)を
  実行する。CI は `gen` を実行しない(食い違いの検出だけが役割)。ツール自体の
  検証は lockfile の integrity 照合(frozen install)→ `self-test` の順とし、
  古いツールが新しいツールを承認する循環を避ける

## レイアウトと配布の不変条件

外部に対する不変条件は次の1つに集約する。

> 各 `skills/<name>/` は常に自己完結している(スキルディレクトリ外への
> パス参照を持たない)。

これはスキルを複製して持っていく方式のインストーラが `skills/` という慣習の位置だけを
探索する場合でも壊れないための条件である。編集対象と生成物を別ツリーに分けるレイアウト
(dist 方式)は、この不変条件を配布経路によっては満たせないため採用しない。

### 配布経路

配布は特定の経路を主としない。次の4系統すべてを同格で支え、利用者が選ぶ。

| 経路 | 導入の仕組み | 更新の届き方 |
|---|---|---|
| Claude Code / Codex CLI | plugin marketplace(リポジトリ内の配布メタデータを読み、スキル集をまとめて導入する仕組み) | 宣言された版の更新 |
| OpenCode | 設定にリポジトリを書き、同梱の登録スクリプトが `skills/` を登録する | 参照先の更新 |
| APM(Agent Package Manager。複数のエージェント向けのスキルを1つの宣言から管理する) | リポジトリを依存として宣言し、解決結果を lock ファイルに固定する | タグまたはコミットの付け替え |
| コピー(`gh skill` / `npx skills`) | スキルを導入時に複製する | コマンドの再実行 |

分離した3リポジトリのうち agentic-rules が全経路を支えているため、本リポジトリだけが
一部の経路を欠く状態を作らない。経路の充足は率ではなく、経路ごとに通るか通らないかで
判定する。

配布される版の正本は `.claude-plugin/plugin.json` の version フィールド1箇所とする。
`marketplace.json` と `package.json` はその追従者であり、第2の正本ではない。正本が
1箇所という条件は経路が増えても変えず、追従者との一致は機械検査で担保する。

### 配布面と測定面の分離

本リポジトリは測定器の検出力を証明するため、命名規約に違反するスキルを意図的に
抱えている。これらは fixture(測定器を走らせる対象として用意した合成のスキルツリー)の
一部であり、規約に合わせて直すと検証能力そのものが消える。

複製方式のインストーラの探索範囲は一様ではない。plugin の配布メタデータを入口にして
そこが指す `skills/` だけを見るものがある一方、リポジトリ内の任意の階層にある
`skills/` を走査するものもある。後者では fixture が配布物として露出し、配布前の
検証にも落ちる。

そこで fixture ツリーは名前が `.` で始まる位置に置き、既定の探索から構造的に外す。
確認したインストーラはいずれも既定では `.` で始まるディレクトリを辿らないため、
文書上の但し書きではなく構造で分離できる。探索範囲を明示的に広げるオプションを
付けた場合は fixture も見えるが、それは利用者が範囲を広げたという明示的な選択である。

対価として、fixture ツリーは既定の探索が届かない位置へ移る。fixture 群が本リポジトリの
成果物であることは、以後この文書が主張するのみとなり、発見可能性では示されない。
この対価を承知の上で選んでいる。

### 規模指標の扱い

vendoring(正本の共有文書を各スキル配下へ展開する機構)が生成する行数について、
レイアウト移行を判断する閾値は設けない。閾値を超えたときに取る行動である dist 方式が
既に不採用と決まっており、発火先が存在しないためである。

代わりに残すのは、契約本文を短く保つ規律である。1つの契約が何スキルに展開されるかを
fan-out と呼ぶと、契約本文を1行削るごとに生成行数は fan-out の分だけ減る。

スキル本文の長さについても機械検査は設けない。既知の指摘を抑制して新規分だけを見せる
仕組み(baseline)は指摘の位置で照合するため、値そのものが意味を持つ指摘では、一度
抑制すると悪化しても黙る。値の変化を検出できるようにすることが、機械検査を設ける
前提条件となる。

## スキルの命名

スキル名は `ba0918-<領域名>` とする。`ba0918` は所有者のユーザー ID で、
平坦なグローバル名前空間での名前衝突を避けるためだけに置き、変わらない。
名前は小文字英数字とハイフンからなり、ディレクトリ名と一致させる。

領域名は移植元 claude-skills でのスキル名をそのまま引き継ぎ、語数で
切り詰めない。移植は既存スキルの移設であり、どのスキルの移植先かを名前だけで
辿れることを名前の短さより優先する。agentic-rules が領域名を1〜2語に制限するのは、
あちらが共有文書からスキルを起こし直して名前を新しく与えたためであり、
本リポジトリはその制限を引き継がない。

## 言語

`docs/spec/` は日本語。それ以外(スキル本体を含む)は英語とする。
