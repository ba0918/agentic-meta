# スキルのトークン効率監査

## 目的

`ba0918-skill-token-efficiency-audit` は、AIエージェントの作業手順をまとめた「スキル」を分析し、品質を保ちながらトークン効率を改善できる余地を利用者へ示す。

トークンとは、AIモデルが文章を処理するときの文字列の単位である。この仕様でいうトークン効率は、単に文章を短くすることではない。必要な品質を満たして仕事を完了するまでに使う、入力と出力の総トークンを対象とする。

このスキルは `agentic-meta` に置く。`agentic-meta` は、AIエージェントの能力を測定・評価・改善するスキルを収めるリポジトリである。

## 責務

このスキルは、指定されたスキルを読み取り専用で分析し、次の情報を会話へ提示する。

- トークン効率を改善できる余地
- 非効率が生じる因果関係
- 分析を支える証拠と、その確かさ
- 改善案
- 品質とのトレードオフ
- 改善案を採用する前に必要な検証
- 移行中だけ存在する問題か、移行後も残る問題か

分析結果を提示した時点で、このスキルの仕事は完了する。利用者は、その結果を引き継いで壁打ちと実装計画の作成を行う。

## 責務に含めないこと

このスキルは、次の操作を行わない。

- 対象スキルの変更
- 改善案の自動適用
- 新しい評価実験の起動
- 対象スキルに含まれる実行可能なプログラムの起動
- 別のAIモデルやエージェントの起動
- ネットワークへのアクセス
- 壁打ちや実装計画の作成
- 永続的なレポートやキャッシュの作成

既存の測定結果は利用できる。ただし、測定自体は既存の評価スキルの責務とする。

## 入力

### 必須入力

利用者は、分析するスキルの名前またはパスを指定する。

スキル名から対象を一意に特定できない場合、このスキルは候補を推測せず、必要な場所を利用者へ確認する。

### 任意入力

利用者は、次の証拠を追加で指定できる。

- 既存の評価シナリオ
- 過去の入力・出力トークン数
- 呼び出し回数
- 再試行数
- 評価結果
- 前回の監査結果
- 必要部分だけを抽出した実行記録

実運用データは、匿名化された集計値を優先する。生のセッション履歴は、AIエージェントとの会話や操作記録を保存したデータであり、機密情報を含む可能性がある。そのため、利用者が対象パスと読み取り許可を明示した場合に限って読む。

既定の実行では、ホームディレクトリや他の保存領域からセッション履歴を自動探索しない。

## 分析範囲

### 起点

対象スキルの中心となる `SKILL.md` を必ず全文読む。`SKILL.md` は、そのスキルの発火条件と実行手順を定める主文書である。

### 明示的に到達できる範囲

`SKILL.md` を起点として、実行時に明示的に参照、実行、または委任される先を再帰的に辿る。

対象には次が含まれる。

- 参照文書
- 出力形式を定める契約
- 実行可能なプログラム
- 評価シナリオ
- 委任先として指定された別スキル
- 実行手順に含まれる外部コマンド

別スキルは、呼び出しによる費用の仕組みを確認するために扱う。明示的な理由がない限り、その別スキル全体の監査へ範囲を広げない。

対象スキルから到達できないディレクトリやリポジトリ全体は走査しない。

### 特殊な参照

循環参照は、同じ対象を一度だけ分析する。循環によって実行時の再読が起こり得る場合は、それ自体を改善候補として報告する。

実行時に組み立てられるため静的に解決できないパスは、推測で展開しない。未解決の依存として報告する。

## 段階的な読み取り

対象の `SKILL.md` と、実行時に常に全文を読むよう指定された契約や参照文書は、必ず全文を読む。

それ以外のファイルは、先に次の構造を機械的に調べる。

- ファイルサイズと行数
- 見出し
- 参照関係
- 実行経路上で読む条件
- 読む回数
- 他の処理へ複製される可能性

その後、分析に必要な部分を読む。部分的にしか読まなかったファイルは、読んだ範囲と省略した理由を報告する。

「会話へ全文を入れない」ことと「何も調べない」ことを区別する。効率化のために情報を段階的に読む場合でも、必須条件や例外を落としてはならない。

固定のトークン上限は設けない。対象の複雑さによって必要な分析量が異なるためである。同じ内容の再読を避け、全文を読む場合は、その必要性を説明できることを効率上の制約とする。

## 分析方法

### 実行経路の再構成

対象スキルの処理を、次の流れとして再構成する。

```text
入力 → 読み取り → 判断 → 分岐・反復・委任 → 出力
```

各処理について、次の要素が費用を増幅していないか調べる。

```text
負荷の形 ≈ 内容量 × 読取回数 × 経路の利用頻度 × 複製先の数 × 再試行
```

これは未計測の削減量を算出する式ではない。費用が増える因果関係を発見するための見方である。

### 原因の発見

既知の原因一覧は、見落としを防ぐ補助として利用できる。ただし、分析対象を固定された分類へ限定しない。

既知の例には次がある。

- 必要以上に大きな入力や出力
- 同じファイルの反復読み込み
- 必要以上に広い走査
- 修正のたびに行う全体レビュー
- 複数エージェントへの同じ情報の複製
- 条件に関係なく読む参照文書
- 不明確な指示による再試行
- 終了条件の不足による反復
- 通常処理と例外処理を常に同じ重さで実行する構造

新しい原因を発見した場合は、既存分類へ無理に当てはめず、因果関係をそのまま記述する。

### 重複の扱い

同じ情報が複数箇所にあることだけを理由に、削除を提案しない。

重複が安全性、独立したレビュー、障害時の復旧などに必要な場合がある。品質上の役割を確認し、より少ない費用で同じ役割を果たせる場合にだけ改善候補とする。

## 品質の扱い

品質を一つの点数へまとめず、次の二層に分ける。

### 必須品質

低下すると対象スキルの目的を満たせなくなる品質である。

例：

- 安全性
- 正確性
- 完了条件
- 主要な利用場面
- 必須の確認手順
- 禁止事項の保持

必須品質が下がる改善案は、原則として不採用候補とする。

### 選好品質

低下しても、対象となる利用場面を満たせる可能性がある品質である。

例：

- 説明の詳しさ
- まれな利用場面への対応
- 網羅性
- 利便性

選好品質と引き換えに効率が上がる案は、トレードオフとして提示する。利用場面を十分に満たす場合は、用途を限定した採用候補にできる。

### 品質基準の取得順

品質基準は次の順で探す。

1. 既存の評価シナリオ
2. 明文化された契約
3. 利用者が指定した利用場面
4. `SKILL.md` が説明する目的と利用場面
5. 実行履歴から確認できる利用傾向

評価シナリオや契約が存在しない場合は、`SKILL.md` から仮の主要利用場面を抽出できる。ただし、その品質基準が未確認であることを明示する。

実行履歴で利用頻度が低いことを、不要な利用場面を示す証拠として扱わない。

## 証拠の確かさ

各分析結果を、次のいずれかに分類する。

| 区分 | 意味 |
|---|---|
| 実測 | 利用者が指定した実行結果やトークン数で確認できた |
| 導出 | ファイルサイズや明記された反復回数などから機械的に求めた |
| 仮説 | 静的な構造から改善の可能性を推測した |

実測には、可能な範囲で測定期間、試行数、対象スキルの版を添える。

未確認の利用頻度、再試行率、削減トークン数を、確認済みの値として扱わない。

## 移行中の問題

分析対象が移行中の場合、各結果を次のように区別する。

- 移行完了後も残る構造的な問題
- 旧経路と新経路の併存など、移行中だけの問題
- 移行状態を確認できず、継続性を判断できない問題

移行中だけの問題に対する最適化は、移行完了前に投資する価値があるかを判断材料へ含める。

## 出力

### 全体判定

出力の先頭に、次のいずれかを示す。

| 判定 | 意味 |
|---|---|
| 改善推奨 | 必須品質を守れる根拠があり、支持できる改善候補がある |
| 評価後に判断 | 改善候補はあるが、効果または品質への影響を確認する必要がある |
| 支持できる改善候補なし | 調査範囲内では、変更を支持する十分な候補がない |
| 判定不能 | 必須情報が不足し、全体判定を支えられない |

「支持できる改善候補なし」は、改善不可能であることを証明する判定ではない。調べた範囲と証拠の限界を併記する。

### 改善候補

各候補へ、同じ監査結果内で変わらない識別子を付ける。後続の壁打ちでは、この識別子を使って候補を参照できる。

各候補は次を含む。

- 現在の処理
- トークン費用が増える因果関係
- 根拠の場所
- 証拠の区分
- 確度
- 改善案
- 期待できる効果
- 必須品質への影響
- 選好品質への影響
- 採用前の検証方法
- 移行完了後も残る問題か
- 現時点の判断

数値を支える実測または機械的な導出がない場合、削減トークン数を断定しない。

### 調査範囲

最終結果には次を含める。

- 全文を読んだファイル
- 部分的に読んだファイルと範囲
- 構造だけを測定したファイル
- 読めなかったファイルと理由
- 解決できなかった参照
- 使用した任意の実測データ
- 分析対象のおおよその入力規模

原文、会話本文、セッション識別子、秘密情報は転載しない。

### 後続の判断材料

改善候補がある場合、最後に次を示す。

- 壁打ちで決める論点
- 採用時に固定する必須品質
- 比較する現行案と改善案
- 評価する利用場面
- 取得するトークン指標
- 採用・棄却条件
- 利用できる既存の評価スキル

この情報を提示した後、このスキル自身は壁打ちや計画作成を開始しない。

## 失敗時の扱い

対象が存在しない場合は、分析を開始せず、確認できなかった対象を報告する。

一部の参照を読めない場合は、確認できた範囲の部分結果を返す。読めなかった範囲が全体判定へ与える影響を明記する。

必須品質または主要な実行経路を確認できない場合、全体判定を「判定不能」とする。

循環参照、動的なパス、解析できない形式があっても、それだけで結果全体を破棄しない。確認できた事実と未確認事項を分けて報告する。

## 代表的な評価対象

初期評価では、次の性質を持つスキルを一つずつ扱う。

- 頻繁に参照される規則型スキル
- 多数の参照文書、評価手順、実行可能なプログラムを持つ測定型スキル
- 分岐、反復、委任、レビューを持つ進行型スキル

評価対象は `agentic-rules`、`agentic-meta`、`agentic-workflow` から選ぶ。これらはそれぞれ、作業規則、能力の測定、作業の進行を扱うリポジトリである。

一つのリポジトリ固有の構造だけで成立させず、未知の第三者製スキルでも同じ入力契約と出力契約で完了できることを確認する。

## 完了条件

次の条件をすべて満たしたとき、監査を完了とする。

- 指定スキルと調査した範囲を示した
- 実行経路上のトークン増幅要因を調べた
- 各分析結果に根拠の場所、証拠の区分、確度を付けた
- 各改善候補に期待効果、品質への影響、検証方法を付けた
- 移行中だけの問題と構造的な問題を区別した
- 未確認値を推測で埋めなかった
- 読まなかった範囲と理由を示した
- 対象の変更、新規評価、外部処理、永続的な出力を行わなかった
- 改善候補がない場合も、その結論と調査範囲を報告した
